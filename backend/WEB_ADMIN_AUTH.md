# Web administrator authentication and offline setup

The Java web-admin authentication, React Administrator Login and Hospital Review
Dashboard are implemented. The role-selection flow links to `#/admin/sign-in`;
an authenticated ACTIVE ADMIN opens `#/admin`. The React hospital registration
form at `#/hospital/register` submits applications independently of staff signup.

The operator has verified administrator login, real Oracle application listing,
and website approval/rejection against local Oracle XE 21c / XEPDB1. See
[the review API document](ADMIN_HOSPITAL_REVIEW.md#verified-local-demonstration)
for the recorded demonstration results. Automated test doubles are separate
from that operator-reported live verification. This documentation update did
not query or change Oracle.

## Local-only opt-in

`WEB_ADMIN_ENABLED` defaults to false. The existing backend behaves as before for
citizens and hospital staff; administrator login and the administrator-only
session endpoint are denied until the flag is explicitly true.

With administrator access enabled, startup refuses a bind address other than
127.0.0.1, localhost or ::1. Every administrator login/session request checks both
socket addresses are loopback and any supplied Origin is a canonical local
http/https origin. The existing exact CORS allowlist still applies first. No
forwarded-IP header is trusted. This is local academic demonstration protection,
not a production security boundary or a replacement for restricted Oracle users.

## Endpoints and session policy

* POST `/api/auth/login`: existing CSRF-protected and throttled login, now permits
  ADMIN as an expected account type only when local administration is enabled.
  AuthDao verifies the password, ACTIVE state and actual stored role. A JSON role
  does not grant permission; forged IDs/status fields do not establish identity.
* GET `/api/auth/me`: existing session bootstrap/introspection, now supports a
  validated ADMIN. Invalid/revoked/changed-role sessions become a fresh guest
  cookie/CSRF response with HTTP 401; staff assignment failures remain denied.
* GET `/api/admin/auth/me`: protected administrator session introspection. It
  requires local opt-in, an ADMIN-authenticated session and a fresh Oracle check
  for ACTIVE/ADMIN. Guests receive 401; citizen/staff sessions receive 403.
  The central `/api/admin/` guard protects all review routes below.
* POST `/api/auth/logout`: existing CSRF-protected logout destroys the server
  session and expires the cookie. It does not require a database write.

Sessions retain the Oracle-authenticated role at login. Each authenticated user
lookup compares it with Oracle's current role and status; role changes require
fresh login and cannot promote an existing citizen/staff session. Administrator
cookies and server-side sessions have a 30-minute absolute lifetime; citizen and
staff lifetimes remain eight hours and guest sessions remain thirty minutes.
Login rotates both session ID and CSRF token. Tokens/IDs are generated by the
existing SecureRandom implementation. Passwords use the unchanged salted PBKDF2
utility and existing account/IP failure limits. Cookies remain HttpOnly,
SameSite=Lax, with Secure controlled by the existing COOKIE_SECURE setting.

The same ADMIN-only guard protects these implemented Java routes:

* GET `/api/admin/hospital-registration-requests`: status-filtered, bounded list.
* GET `/api/admin/hospital-registration-requests/{id}`: full review details and
  session-bound stale-review token.
* POST `/api/admin/hospital-registration-requests/{id}/approve`: local-demo
  approval with CSRF, explicit confirmation, duplicate checks and one atomic
  hospital/application transaction.
* POST `/api/admin/hospital-registration-requests/{id}/reject`: CSRF-protected
  rejection with reason, server-owned notes and no hospital creation.

See [ADMIN_HOSPITAL_REVIEW.md](ADMIN_HOSPITAL_REVIEW.md) for exact JSON contracts.
There is no public administrator signup or account-promotion endpoint. Public
registration still fixes CITIZEN/ACTIVE or HOSPITAL_STAFF/PENDING_VERIFICATION
regardless of supplied privileged fields. Staff registration/login remain
separate. The restricted CLI still refuses SYSTEM and is not used by the website.

## Offline account creation (intentional operator action only)

The setup utility lives under `backend/tools`, outside the public Maven/launcher
source root and runtime classpath. It is not the restricted administrator CLI.
It creates one new application USERS row, not an Oracle user/role or staff/hospital
record. It never updates/promotes an existing email/account.

For a separately authorized new administrator account, open
a trusted interactive PowerShell terminal with no transcript or recording:

```powershell
$env:WEB_ADMIN_ENABLED = 'true'
$env:ORACLE_URL = 'jdbc:oracle:thin:@//localhost:1521/XEPDB1'
$env:ORACLE_USER = 'SYSTEM'
# Keep OJDBC_JAR pointing to the existing trusted Oracle JDBC jar.
# Run from backend/:
.\tools\create-web-admin.ps1
```

The utility requires its explicit operation flag (supplied by the launcher), a
real console, local XEPDB1 URL, SYSTEM identity, and the exact confirmation phrase
CREATE LOCAL WEB ADMIN. It separately prompts without echo for the new admin
password/confirmation and the existing local database password. It never reads
ORACLE_PASSWORD, prints secrets/hashes, accepts password arguments, or saves a
credential file. The actual connection must confirm normal SYSTEM authentication
in XEPDB1 without proxy/SYSDBA. Field/password validation, duplicate-email checks,
and a single prepared INSERT use the existing PBKDF2 hashing and SEQ_USERS.
The insert fixes role ADMIN and status ACTIVE in SQL. Commit occurs only after
one affected row; failures roll back. Oracle sequence gaps after failure are normal.

Password character buffers are cleared on completion/failure. JDBC and PBKDF2
necessarily create temporary immutable Java Strings; those cannot be reliably
wiped, so keep the console/JVM and trusted driver restricted. Errors print only
fixed validation messages or Oracle numeric codes, never JDBC exception text,
stack traces or connection credentials. An ambiguous commit failure requires
checking account existence before retrying. There is no default password or
automatic existing-account password reset.

To enable server authentication, set WEB_ADMIN_ENABLED=true only in its
local process and retain its existing ORACLE_* connection settings. No Oracle
provisioning, SYSTEM password change, grant, migration or frontend environment
change is required. Do not put database credentials in VITE_* variables.

## Focused verification

From `backend/`:

```powershell
.\run-web-admin-auth-tests.ps1
```

The runner compiles production sources and the offline utility separately with
`--release 17`. It runs only new focused setup/authentication tests with the
test-only OracleDriver, a forced TEST-ONLY JDBC URL and loopback HTTP test ports
18091/18092. No real JDBC jar appears on the test classpath. Settings are restored
on exit, and the test servers exit after testing. It also checks that the setup
utility and restricted AdminCli cannot load on the web runtime classpath.

Coverage includes default-disabled/admin-enabled behavior, local binding/origin
checks, genuine/forged roles, unchanged citizen/staff authentication, inactive
accounts, session rotation/expiry/revocation, logout, throttling, absence of public
admin signup, public signup role isolation, secure setup hashing, password buffer
cleanup, duplicate prevention and setup rollback/fault paths. No citizen portal,
inventory, emergency routing or FEFO functional suite is run. The shared test
driver only gains a test-only bound-parameter capture map.

## Remaining limits

The backend still uses SYSTEM locally. Correct endpoint authorization does not
remove SYSTEM's schema-owner powers if the backend or its credentials are
compromised. Database/user permissions remain a separate deployment concern.
Login throttling and sessions are in memory and reset when the process restarts.
The local demonstration does not establish production-ready security, automatic
government verification or comprehensive live concurrency/fault coverage. Live
results are recorded separately from automated test-double results. The backend
launcher uses the existing process-only ORACLE_* settings; never expose database
credentials through frontend configuration or commit environment files.
